## Tiers

1. **Grammar** (tree-sitter): definitions with kinds, qualified names, signatures, documentation, call edges and imports as listed per language below. `cargo test` re-verifies every row with a sample file (`tests/samples.rs` compares the parse of `tests/samples/<file>` with `expected.json`).
2. **Heuristic**: a language without a grammar in this build gets keyword-introduced definitions (`def`, `fn`, `function`, `sub`, `proc`, `class`, `struct`, `module`, Lisp `(def...`, SQL `CREATE ...`, shell `name() {`) with the indented block below them, and no call edges or imports. A comment block right above a keyword definition is its documentation and ends the definition above it; the comment marks are the shared ones (`//`, `#`, `--`, `;`, `/* */`, `*`, `%`) plus, by extension, `(* *)` for ML, F#, TLA+ and Pascal, `{ }` for Pascal, `!` for Fortran (and `c` in column 1 for fixed form), `"` for Vim, `{- -}` for the Haskell family, `<# #>` for PowerShell, `#| |#` for Lisp, `#[ ]#` for Nim, `/+ +/` for D and `%{ %}` for MATLAB. A custom language (a `[[language]]` table in the root's `.scrutate.toml` or your configuration file, see [CLI](CLI.md#custom-languages)) is read this way too, its own definition patterns and comment marks replacing the keywords and shared marks.
3. **Windows**: every other readable text file is indexed as overlapping 50-line windows, so Engine B can search it (Engine A always can). In the first two tiers, lines no definition's chunk keeps (code outside the definitions, the rest of a long one) are windows too, named after their definition or file.

Engine A (instant search) needs none of this: it searches every readable file, in any language or none.

A `.h` file is read as objc when a line matches `(?m)^[ \t]*@(?:interface|protocol|implementation|class)\b`, else as cpp when a line matches `(?m)^[ \t]*(?:namespace\b[^;]*\{|namespace\s+\w[\w:]*\s*$|class\s+\w+|template\s*<|using\s+namespace\b|(?:public|private|protected)\s*:|extern\s+"C\+\+"|#\s*include\s*<[a-z_]+>)`, else as c (`sniff` in `crates/scrutate/src/langs.rs`).
A `.m` file is read as objc when its first 4000 bytes hold `@interface`, `@implementation`, `#import`, `@end`, `@protocol`, else as matlab. A `.pp` file is read as pascal when a line of its first 4000 bytes matches `(?im)^[ \t]*(?:unit|program|library)[ \t]+[\w.]+[ \t]*;` (a unit, program or library header), or when it holds `procedure `, `function `, `begin`, `end;`, `unit `, `program ` and its first 4000 bytes hold no `$`; else as puppet.

## Definitions written as assignments or under another owner

- Lua: a function assigned to a name (`local f = function`, `M.f = function`, `M["f"] = function`) or given as a table field (`f = function` inside `local obj = {...}`) is a definition, owned by what holds it (`M.f`, `obj.f`). In a multiple assignment (`local a, M.b = function ... end, function ... end`) each function is named by the target in its position.
- JavaScript and TypeScript: a function assigned to a member is a definition: `Foo.prototype.bar = function` is the method `Foo.bar`, `Foo.make = () => ...` is `Foo.make`, `obj["k"] = function` is `obj.k`, `exports.f` and `module.exports.f` are `f`, and `exports.a.b` is `a.b`. `this.x = function` inside a function or class is the method `x` of that function or class (`Widget.x`, `Panel.x` from its constructor). A default export written as an expression (`export default function () {}`, `export default class {}`, `module.exports = () => ...`) keeps its own name, else takes the file's name (`app` for `lib/app.js`, the directory's name for an `index` file). Members of an object assigned to `module.exports` are definitions under their own names. A function under a computed key (`handlers[i] = function`) is not a definition. The comment above such an assignment is the function's documentation.
- Julia: `function Base.show(...)` and `Base.show(...) = ...` are named `show` and owned by `Base`, so `symbol show` and `symbol Base.show` both find them; a method of a quoted operator, `Base.:(==)(a, b) = ...`, is named `==`.
- C++: the call operator is named `operator()`. Haskell: an operator definition (`a <+> b = ...`, `(<+>) a b = ...`) is named by its operator. R: an R6 method in `R6Class("Counter", public = list(add = function(n) ...))` is the method `Counter.add`.
- GDScript: a file's `class_name` is a class whose chunk holds the `extends` line right below it and, when no member follows at once, the comment block below the two, where Godot writes a class's documentation. The file is that class: its top-level definitions are its members (`Player.move`, a method), each its own chunk, and `symbol move` finds them by the bare name too. In a file without `class_name` they keep no owner (`move`, a function). An inner `class` owns its methods (`Player.Backpack.stash`). A `signal` is of kind `signal`, a `var` at file level or in an inner class body a `key`, a `const` there a `constant`, and a named `enum` an `enum`.
- Ruby and Elixir names keep a trailing `?` or `!`, Julia names a `!`, R names their dots, Bash names their `::`, Haskell, OCaml, F# and Nix names their primes; a Rust raw identifier `r#type` is named `type`.

## Known limits

- Heuristic-tier languages get no call graph, no imports and approximate block extents.
- Data keys (JSON/YAML/TOML) nest at most two levels deep.
- A grammar that mis-parses unusual syntax falls back to the module header plus windows for that file (never to invented symbols).
